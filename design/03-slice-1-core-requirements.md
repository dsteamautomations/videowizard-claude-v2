# Slice 1 — server core: requirement list for approval

Scope: the ledger and gatekeeper only. No stages, no providers, no UI, no plugin. When this slice is done, a test client can create a run, ask `next`, commit a stage output with the operator's acceptance quote, view and revise, hit an attempt cap, replay a request safely, and close a run. **Decided 14 Oct:** no paid-action gate and no browser approvals; acceptance is an explicit yes in chat, stored verbatim. The stage table is a data file, so slices 4–8 add stages without changing this code.

## 1. Requirement, restated

Build `videowizard-v2/server`: FastAPI + Postgres, with

- tables from plan §4, all prefixed **`vw2_`** in the existing VideoBuilder Supabase project: `vw2_runs`, `vw2_stage_outputs`, `vw2_approvals`, `vw2_attempts`, `vw2_jobs` (table only, no workers yet), `vw2_defects`, `vw2_procedures`, `vw2_sessions`, `vw2_receipts`; v1 tables untouched;
- endpoints from plan §5 except `/jobs` execution, `/procedures` content and `/files/sign` (those come with their slices): `POST/GET /runs`, `GET /runs/{id}`, `GET /runs/{id}/next`, `POST /runs/{id}/output`, `GET /runs/{id}/stages/{stage}` (view, read-only), `POST /runs/{id}/revise`, `POST /runs/{id}/adopt`, `POST /runs/{id}/close`, `POST /runs/{id}/defects`;
- the state machine driven by a stage table (`stages.json`: order, needs_acceptance, paid, per_unit, cap) loaded per procedure version;
- acceptance by quote: stages flagged `needs_acceptance` require a non-empty `accepted_quote` on `output`; stored as given;
- paid stages carry `paid: true` in the stage table only so `next` can tell the executor to *inform* the operator; the server does not gate on it;
- attempt caps returning `409 NEEDS_USER_DECISION`;
- idempotent writes by `request_id`;
- login: v1's `auth.py` ported unchanged (shared `employees` directory + `apps.members` role) in this slice; sessions carry `kind` = `executor` or `browser`. Tests seed a session row directly because the local test database cannot reach the shared directory.

## 2. Unstated requirements I will treat as in scope

1. **Run code** (`VW-11`-style short code) generated by the server; the plugin uses it for the folder name.
2. **`next` is the only source of truth for order.** Every write endpoint re-checks `next` server-side and rejects anything not listed (`409 NOT_ALLOWED` with the allowed list).
3. **Per-unit stages** (analysis per media, visuals per shot): `next` returns the stage plus the list of units still open; `output` and `propose` take a `unit`. The stage completes when every declared unit has a non-stale output. Units are declared by the previous stage's output (`summary.units`).
4. **View vs revise** (see 04-slice-1-answers.md Q3). *View* is read-only and always allowed. *Revise* reopens a stage: allowed outright when no paid output exists after it; otherwise 409 with the list of paid outputs that would be obsoleted and their cost, and it proceeds only when the call carries `confirm_quote` (the operator's explicit yes in chat). Revised and later outputs are marked `stale`, stay readable, and `next` returns to that stage. Per-unit revise affects only that unit.
5. **`adopt`** changes `procedure_version` and marks nothing stale by itself; it only changes which `stages.json` drives `next`. If the new table has stages the run has no output for, `next` surfaces them.
6. **Acceptance quote**: for stages with `needs_acceptance`, `output` must carry `accepted_quote` (the operator's reply, verbatim, ≤ 2 KB); the server stores it with `accepted_by` and `accepted_at`. No token, no browser step.
7. **Attempt counting**: `output` and (later) `jobs` increment `attempts(run, stage, unit)`. Cap from `stages.json`. A successful `output` resets the counter for that (stage, unit). `revise` resets counters of the reopened stages.
8. **Idempotency**: every write carries `request_id` (uuid). Same `request_id` + same body → stored response. Same `request_id` + different body → `409 REQUEST_CONFLICT`. Receipts store status code + response only, never the request body.
9. **Owner check**: only the run owner (or admin) may read or write a run. Admin sees all runs in `GET /runs`.
10. **Close** requires: every retained file listed in stage outputs has a storage receipt (slice 1: a `receipt` flag on the file entry; real storage verification arrives with `/files/sign`). Closed runs reject all writes except `reopen` (admin).
11. **Timestamps** UTC in the database; API returns ISO-8601 with `Z`.
12. **Migrations** as plain SQL files applied in order by a tiny runner (no framework); every function is defined once (no paste-forward of bodies, which the v1 review flagged).
13. **Cost field** on stage outputs stays nullable in slice 1.

## 3. Edge cases (each becomes a test)

| # | Case | Expected |
|---|---|---|
| E1 | `next` on a new run | stage 1, actor `operator`, attempts 0/cap |
| E2 | `output` for a stage that is not next | 409 `NOT_ALLOWED`, body lists allowed actions |
| E3 | `output` for a stage with `needs_acceptance`, no `accepted_quote` | 422 `ACCEPTANCE_REQUIRED` |
| E4 | `accepted_quote` longer than 2 KB or whitespace only | 422 |
| E5 | `output` for a paid stage | 201; `next` had flagged `paid: true` with the provider name so the executor informs the operator; nothing gated |
| E6 | `output` stores `accepted_by` = session user, `accepted_at` = server time | fields present on `GET /runs/{id}` |
| E9 | failed `output` × (cap+1) on one stage (validation failures count) | last call 409 `NEEDS_USER_DECISION` with options `[retry, revise, defect, stop]`; `next` reports `actor: operator_decision` |
| E10 | After `NEEDS_USER_DECISION`, `output` again without a decision | 409 again (no silent retry) |
| E11 | Decision `retry` (a `POST /runs/{id}/decide`) | one more attempt allowed, then cap again |
| E12 | Successful `output` | attempts for that (stage, unit) reset to 0 |
| E13 | Per-unit stage with 3 units; 2 outputs committed | `next` still that stage, `units_open: [u3]` |
| E14 | Per-unit stage, output for an undeclared unit | 422 `UNKNOWN_UNIT` |
| E15 | `revise` stage 2 from stage 3, no paid outputs after 2 | outputs of 2–3 stale; `next` = stage 2; attempts of 2–3 reset |
| E16 | `revise` a stage with no output yet | 409 `NOT_ALLOWED` |
| E16a | `revise` stage 3 (script) after stage 4 (voice, paid) has an output | 409 `PAID_WORK_AFTER` listing the paid outputs and cost; nothing changes |
| E16b | Same call with `confirm_quote` (operator's explicit yes) | proceeds as E15; quote stored on the revise record |
| E16c | `revise` one unit of a per-unit stage | only that unit stale; other units and later stages untouched unless they declare a dependency on that unit |
| E16d | `GET /runs/{id}/stages/{stage}` on a stale or closed stage | 200, read-only, no state change |
| E17 | Same `request_id`, same body, twice | identical response, one row written |
| E18 | Same `request_id`, different body | 409 `REQUEST_CONFLICT` |
| E19 | Two concurrent `output` calls for the same (run, stage, unit) with different request ids | exactly one succeeds; the other 409 `NOT_ALLOWED` (stage already done) |
| E20 | Non-owner reads a run | 404 (not 403, so run ids are not probeable) |
| E21 | Admin lists runs | sees all; owner sees own |
| E22 | `close` with a file lacking receipt | 409 `UPLOAD_INCOMPLETE` listing the files |
| E23 | Write to a closed run | 409 `RUN_CLOSED` |
| E24 | `adopt` to an unknown version | 404 `VERSION_UNKNOWN` |
| E25 | `adopt` to a version whose table has a new stage before the current one | `next` returns the new stage |
| E26 | `output` body (summary + files list) larger than 256 KB — guard against blobs in the database; files go to storage. Approved 14 Oct; it is a setting | 413 |
| E27 | Unknown stage name in `output` | 422 |
| E28 | Empty `files[]` on a stage that declares outputs | 422 `FILES_REQUIRED` |
| E29 | `defects` from an executor | row created, `next` unchanged, response includes ticket number |
| E30 | Session token unknown / expired | 401 |

## 4. Failure modes and handling

| Failure | Handling |
|---|---|
| Database down | 503 with `retry_after`; no partial writes (each write is one transaction) |
| Partial write mid-transaction | Postgres rollback; receipt not stored, so the client retries with the same `request_id` |
| Clock skew between executor and server | server time only; the client never sends timestamps |
| Stage table missing for a version | 500 `PROCEDURE_INVALID` at `adopt`/create time; cannot create a run on a broken version |
